# 사이드 장문 대화와 컨텍스트 예산

2026-09-11 수정. 원래 구현은 요청 JSON의 문자 수를 그대로 token으로 간주하고 작업의 32K 출력 예약을 물려받아서, HTML·JS·도구 결과가 많으면 정상적인 사이드 질문도 일찍 거부했습니다.

## 오픈소스 구현 대조

- [Grok CLI 사이드 컨텍스트](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 최근 사용자·어시스턴트 텍스트에서 조각을 뽑고, 문자 예산은 약 2000, 항목마다 최대 400자까지 자릅니다. 이 경로에서는 연속된 사이드 Q&A 이력을 유지하지 않습니다.
- [Grok CLI 독립 요청](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): 독립 취소 신호, 모델이 지원하면 출력 상한 2048 tokens, 도구 미제공.
- [Grok CLI 메인 세션 압축](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): token을 추정하고 최근 내용을 유지하며, 새 내용을 오래된 요약에 갱신하고 턴을 넘는 절단을 처리합니다.
- [OpenCode 세션 압축](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): 전체 요청 추정, 출력/버퍼 예약, 최근 내용 + 롤링 요약, 도구 없는 요약 요청. 이 구현의 기본 최근 예산은 8000, 요약 출력 상한은 4096 tokens입니다.
- [OpenCode 오버플로 복구](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): 아직 어시스턴트 출력이 시작되지 않았을 때만 오버플로 복구를 시도하고, 복구된 호출은 같은 오버플로 복구 경로에 다시 들어가지 않습니다.

ARTEX는 독립 출력 예산, 최근 내용 + 롤링 요약, 제한적 복구 방식을 참고했습니다. norma v0.3.6의 구조화 메시지와 도구 짝은 유지하고 Grok식 텍스트 발췌를 그대로 옮기지 않았습니다. OpenCode의 메인 세션 압축 이벤트를 ARTEX 메인 transcript에 쓰지도 않습니다.

## 요청 예산과 실행

- 메시지는 norma의 콘텐츠 블록별 UTF-8 바이트 추정과 4/3 여유를 그대로 씁니다. 시스템 프롬프트, 도구 schema와 메시지 봉투 오버헤드도 추가로 계산합니다. 추정치는 모델의 정확한 token 수가 아닙니다.
- 사이드 출력은 기본 최대 8192 tokens이고, 메인 설정에 이미 있는 출력 상한을 넘지 않습니다. 서비스 환경 변수 `ARTEX_BTW_MAX_OUTPUT_TOKENS`로 256–32768 상한을 설정할 수 있습니다. 제품 기본 모델이나 메인 작업 파라미터는 바꾸지 않습니다.
- 입력 예산은 컨텍스트 윈도에서 출력 상한과 안전 여유를 뺀 값입니다. 알 수 없는 윈도는 플랫폼 기본 200K를 씁니다. 안전 여유는 윈도의 5%, 최소 128, 최대 8192 tokens입니다.
- 성공한 Q&A는 증가하는 순번 기준으로 배치당 최대 20쌍을 불러옵니다. 원문은 최대 20쌍을 유지하고, 그 token 예산은 입력 예산의 1/4을 넘지 않으며 16K도 넘지 않습니다.
- 초과한 Q&A는 롤링 요약으로 갱신합니다. 요약에는 이력 출처와 컨텍스트 시각이 붙습니다. 이력에 있는 어시스턴트 답변은 새로운 도구 증거와 같지 않으며, 충돌하면 최신 메인 스냅샷을 우선합니다.
- 메인 컨텍스트가 여전히 길면 사본의 오래된 메시지만 요약하고 최근 것은 최대 8K tokens까지 남깁니다. 절단 지점은 도구 호출과 결과를 갈라놓지 않습니다. 너무 큰 단일 묶음은 통째로 요약에 들어갑니다.
- 요약 입력은 실제 남은 윈도에 맞춰 UTF-8 안전하게 청크로 나누고, 출력 상한은 2048 tokens입니다. 빈 요약, 절단, 도구 호출, 요약 예산 초과는 캐시에 쓰지 않습니다. 사이드 하나당 요약 호출은 최대 12회이고 같은 120초 타임아웃을 받습니다. 상한에 닿으면 분명히 실패하고 무한 반복하지 않습니다.
- 모델이 처음 컨텍스트 초과를 돌려주었고 아직 텍스트나 도구 호출을 출력하지 않았으면, 더 줄여서 최대 한 번 재시도합니다. 추정 크기가 줄지 않으면 복구를 즉시 멈춥니다. 다른 모델 오류와 부분 스트리밍 출력은 이 복구를 타지 않습니다.
- 수집한 모든 사용량(요약, 실패 시도, 취소 시점의 사용량 포함)은 같은 사이드 요청에 합산합니다. Provider가 사용량을 돌려주지 않으면 여전히 0으로만 기록하며, 추정치를 실제 사용량처럼 기록하지 않습니다.

## 저장과 API

`side_question_sessions.memory`는 오래된 Q&A 요약, 덮어쓴 ordinal, 스냅샷 식별 정보별로 캐시한 메인 컨텍스트 요약을 저장합니다. `side_question_requests.context_info`는 준비 단계, 실제 재생 묶음 수, 요약 사용 내역과 예산 추정을 저장합니다.

요약은 원래 요청이 아직 실행 중이고 정리 버전이 맞을 때만 저장합니다. 비우기는 캐시도 함께 지우고, 늦게 도착한 쓰기가 정리된 데이터를 되살리지 않습니다. 새 스냅샷은 예전 스냅샷 요약을 재사용하지 않습니다. 요약 필드는 v3 작업 아카이브에 함께 저장되고, 새 필드가 빠진 예전 v3를 복구할 때는 빈 객체로 채우며 v1/v2는 계속 지원합니다.

POST는 먼저 요청을 받아들이고 반환하며, 준비와 압축은 백그라운드에서 실행되고 요청 수락 잠금이나 데이터베이스 트랜잭션을 잡지 않습니다. SSE/이력은 준비, Q&A 정리, 사본 압축, 답변 단계를 표시하고, 압축 실패는 그 사이드 요청의 실패 종료 상태로 저장합니다. 프런트엔드는 오류를 남기고 이번에 실패한 질문의 초안을 복구하며, 떠 있는 알림으로 입력창을 가리지 않습니다. 이력 폴링이 제출 오류를 지우지 않습니다.
