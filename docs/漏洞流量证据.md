# 취약점 다중 트래픽 증거

취약점 상세의 「연결 트래픽」은 페이지를 넘나드는 다중 선택, 용도와 설명, 정렬, 연결 해제를 지원합니다. 트래픽 페이지에서도 기록을 다중 선택해 기존 취약점 하나에 한 번에 연결할 수 있습니다. 작업에서 상속된 취약점 증거는 읽기 전용이며, 수정하려면 원본 작업으로 들어가야 합니다.

시스템 설정의 「에이전트 자동 트래픽 바인딩」은 기본적으로 꺼져 있고, 조회/수정 API는 `/api/settings`의 `agent_traffic_binding`입니다. 켜면 요청/응답 열람, 도구 호출, 프롬프트로 인한 Token 소비가 늘어나며, 다음 에이전트 실행부터 새 설정이 적용됩니다. 끄면 자동 바인딩 파라미터와 재바인딩 도구가 숨겨지고 자동 바인딩 안내가 주입되지 않으며, 이미 실행 중인 세션이 새로 제출하는 자동 바인딩은 거부됩니다. 수동 바인딩, 트래픽 캡처, 저장된 증거 읽기 및 내보내기는 영향을 받지 않습니다.

켜면 기본 흐름은 「발견 및 저장 → 보고 에이전트 자동 실행 → 트래픽 확인 후 바인딩 → 최신 증거 버전으로 보고서 작성」입니다. 보고자는 `evidence`에 검증 명령, 핵심 출력, 이미 확보한 실제 트래픽 ID와 용도를 남기고, 보고 에이전트는 취약점 상세와 실행 기록을 종합해 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고, 최신 `version`을 읽어 보고서를 저장합니다. 스위치를 끄면 보고 에이전트는 원본 트래픽 검색/읽기 도구를 추가로 받지 않고 자동 바인딩도 하지 않습니다. 이때도 수동 바인딩된 스냅샷을 읽어 보고서를 생성할 수 있습니다.

기존 호출자와 호환됩니다. `report_finding`의 `traffic_refs` / `evidence_hint_id`로 여전히 명시적으로 즉시 바인딩할 수 있습니다. 바인딩은 선택 사항입니다. TCP 등 HTTP가 아닌 취약점이거나 캡처되지 않았거나 정확한 기록을 찾을 수 없을 때는 참조를 생략해도 정상적으로 보고하고 보고서를 작성할 수 있습니다. 명령 출력, 로그 등 다른 검증 가능 증거를 남기고, 바인딩하지 못한 이유를 설명하는 것을 권장하며, 필수 필드는 새로 추가하지 않습니다. 제출한 ID는 모두 유효해야 하고 본문도 온전해야 합니다. 하나라도 실패하면 이번 바인딩 작업 전체가 롤백되고, 보고와 함께 명시적으로 바인딩하다 실패하면 보고 전체가 롤백됩니다. 같은 스냅샷을 중복 추가해도 바인딩이 늘어나지 않고 설명도 덮어쓰지 않습니다.

## 에이전트 보고의 ID와 버전

`report_finding`에 선택 파라미터가 추가되었으며, 배열 순서가 초기 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "또 다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(보충 검증), `supporting`(보조 증거, 기본)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 확인하세요. 도메인과 시간은 후보 필터링에만 사용하며, 작업 귀속을 추정하지 않습니다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참고하고 이 프로젝트의 선택적 바인딩 규약을 결합했으며, 패킷 누락 사유를 필수로 검증하지는 않습니다. ID를 추측해서는 안 되고, 패킷을 보충하려고 불필요한 재탐지를 해서도 안 됩니다.

반환 첫 줄은 여전히 `finding recorded: <탐색 노드 ID>`이며, 뒤이어 오는 JSON이 독립 취약점 기록 `finding_id`, 탐색 노드 `finding_node_id`, 바인딩 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 기록 ID**를 사용하며, 정렬된 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`를 넘겨 구간 단위로 읽을 수 있고, 구간당 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 **여전히 탐색 노드 ID를 사용합니다**. 새로 추가된 `evidence_version`에는 실제로 읽은 버전을 넣습니다. 생성 중 증거가 바뀌면 이전 버전 쓰기가 거부되므로 다시 읽고 생성해야 합니다.
- 이전 보고 호출처럼 버전을 넘기지 않으면 기존 트래픽 증거를 덮어쓴다고 간주하지 않습니다. 바인딩, 설명, 용도, 정렬이 바뀌면 기존 보고서에 업데이트 필요 표시가 붙습니다.

자동 바인딩을 켜면 `add_hint` / `add_task_hint`가 단일 힌트 또는 일괄 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있습니다. Planner가 대신 보고할 때는 `evidence_hint_id`를 넘겨 이 작업에 해당하는 힌트의 참조를 명시적으로 고르며, 상속된 힌트는 참조할 수 없습니다. 시스템은 도메인, 시간, 브라우징 기록으로 바인딩을 추측하지 않습니다. 제출이 실패해도 부분 취약점이 생기거나 보고서가 미리 실행되지 않습니다.

기존 취약점에 바인딩이 빠졌을 때는 `bind_finding_traffic(finding_id, traffic_refs)`로 추가 바인딩할 수 있고 다시 등록할 필요가 없습니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명확한 `finding_id`와 `finding_node_id`를 반환하며, 이전 `id`는 탐색 노드 의미를 유지합니다.

프로그램을 시작할 때는 이전 도구 schema에 선택 속성만 추가하고, 원래 기본 트래픽 도구 바인딩을 보고 에이전트까지 확장하며, 재바인딩 도구는 기본적으로 보고 에이전트에게 넘깁니다. 사용자 정의 바인딩 목록, 프롬프트, 설명, 사용 여부는 유지됩니다. 안내는 최종 도구 조립 후 한 번에 추가됩니다. 보고 역할은 확보한 증거를 인계하고, 보고 에이전트는 확인, 바인딩, 보고서 작성을 담당합니다. 플랫폼 대화에 작업 컨텍스트가 없으면 구조화된 힌트로 작업 에이전트에 인계해야 하며 직접 보고하지 않습니다. 작업 완료를 판정하기 전에 확보한 증거를 먼저 인계해야 하고, 패킷이 없다고 강제로 기다리지는 않습니다. 실패한 `report_finding`은 보고 에이전트를 실행하지 않습니다.

## API

기본 경로: `/api/exploration/findings/{finding_id}/traffic` — 독립 취약점 ID를 사용합니다. 인증은 그대로이며, `context_task`가 작업 가시성과 상속 읽기 전용 여부를 검증합니다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서가 채택한 버전 |
| `POST` | `{"traffic_refs":[...]}` 일괄 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}` — 반드시 전체 목록 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 크기 제한 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1`이면 전체 원본 바이트 다운로드 |

버전/정렬 집합 충돌이나 아카이브 중 쓰기는 `409`를, 상속된 대상에 대한 쓰기는 `403`을, 존재하지 않거나 해당 취약점에 속하지 않는 바인딩은 `404`를 반환합니다. 트래픽/첨부 읽기와 검증 실패는 오류를 명확히 반환합니다.

## 저장과 마이그레이션

프로그램을 시작할 때 PostgreSQL에 멱등 마이그레이션을 수행합니다. `traffic_evidence_snapshots`, `finding_traffic_bindings`를 추가하고, `findings.evidence_version` / `report_evidence_version`(기본 0)을 만듭니다. 과거 텍스트를 근거로 추가 바인딩을 추측하지 않습니다.

스냅샷은 원본 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이, SHA-256을 저장합니다. 본문은 해시 기준으로 `<data>/evidence/blobs/<앞 두 자리>/<hash>.bin`에 보관하며, 정리 대상인 `data/traffic`과 독립적이고 여러 취약점이 스냅샷/본문을 공유할 수 있습니다. 스냅샷에는 내용 갱신 API가 없고, 검증이 일치하지 않으면 읽기와 내보내기가 실패합니다.

원본 트래픽 쓰기 잠금 아래에서 대용량 본문 blob과 이전 디렉터리 기록을 포함한 전체 본문을 읽습니다. 파일을 먼저 저장하고 검증한 뒤 단일 PostgreSQL 트랜잭션으로 탐색 노드, 탐색 계획 관계, 취약점, 스냅샷, 바인딩을 씁니다. 커밋 후에야 플래너에 알립니다. 실패하면 참조 없는 파일이 남을 수 있지만 부분적인 작업 기록은 생기지 않습니다.

PostgreSQL advisory lock `7337741004`가 증거 파일과 SQL 참조를 조율하고, 작업 행 잠금이 아카이브 대기 이후의 증거 수정을 금지합니다. 복구는 본문 설치부터 메타데이터 커밋까지 전 구간에서 증거 잠금을 유지합니다. 취약점을 삭제하면 바인딩이 연쇄 삭제됩니다.

정리기는 매시간 실행되며, 참조가 없고 진행 중 작업이 아닌 내용만 최소 24시간 지연 후 회수합니다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않습니다. 핫 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업하세요.

## 내보내기와 아카이브

Markdown에는 정렬된 증거 목록과 버전이, JSON에는 메타데이터가, CSV에는 개수와 바인딩 ID가 포함됩니다. `md-zip`은 취약점 Markdown을 보존하며 다음을 제공합니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 패킷을 참조합니다. 다운로드를 보내기 전에 첨부 복사, 해시 검증, 압축, 디스크 동기화, ZIP 전체 항목의 CRC 읽기 검증을 마칩니다. 누락/손상이 있으면 다운로드 전체가 실패합니다. 온전한 첨부는 이진 원본 바이트를 보존합니다.

아카이브 v3는 취약점 바인딩 관계를 기준으로 스냅샷과 본문을 수집하며 원본 트래픽이나 도메인에 의존하지 않습니다. 패키지 검증이 끝난 뒤에야 핫 데이터를 정리하고, 공유 증거는 계속 보존합니다. 복구는 설치할 본문을 먼저 검증하고 트랜잭션으로 메타데이터와 바인딩을 복원하며, 실패 시 재시도를 지원합니다. v1/v2도 계속 복구할 수 있고, 빠진 새 필드는 0으로 명시해 채웁니다.

## 검증과 경계

테스트 패키지마다 독립적으로 새로 만든 PostgreSQL 테스트 DB를 `ARTEX_PG_DSN`으로 지정해, 잔여 작업/모델 픽스처가 백그라운드 실행을 유발하지 않게 합니다. 관련 패키지의 전체 테스트를 실행하고, 설정 누락으로 인한 건너뛰기가 없는지 확인합니다.

```sh
# 패키지마다 실행 전에 ARTEX_PG_DSN을 해당 독립 테스트 DB로 설정합니다. 설정 실패는 명시적 오류여야 합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증에는 `npx tsc --noEmit`, 변경 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기가 포함됩니다. 실행 중인 개발 서버를 덮어쓰지 않도록 독립 캐시 디렉터리를 사용하세요.

로컬 엔드투엔드 인수 테스트는 독립 포트, 통제된 HTTP / 도메인 HTTPS 대상, 임시 데이터 디렉터리로 수행하며, 두 가지 바인딩 진입점, 페이지 넘김 선택, 정렬/설명, 오류 안내, 상속 읽기 전용, 다운로드, 그리고 원본 트래픽 삭제 후 내보내기·아카이브·핫 본문 회수·복구·해시 검증을 포함합니다.

첫 버전은 전역 증거 조율 잠금을 사용합니다. 대량 바인딩/내보내기나 느린 첨부 다운로드가 진행되는 동안 다른 증거 작업이 대기할 수 있습니다. 녹화 기록이나 온전한 본문이 없을 때 증거를 만들어 내서는 안 됩니다. 이 기능은 캡처 스위치를 바꾸지 않고, HTTPS로 IP에 직접 접속할 때의 인증서 문제도 다루지 않습니다.
